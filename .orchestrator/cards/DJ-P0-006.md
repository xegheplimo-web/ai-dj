## 1. Problem (PROVEN by Hermes, not inferred)

`_silence_check()` in `ai_dj/verify.py` only evaluates silence **inside transition
windows**. `max_run_ms` is updated only when `in_tr[i]` is true, and `silence_ok`
is derived from that single number. Silence inside a track's own content is
counted (`silent_hops_total`) but never used as a fail condition.

**Empirical proof** — a master containing a 29.45 s silent hole:

```
$ python -m ai_dj.cli render --plan evidence/hermes_plan1.json --out old_buggy.wav
$ python -m ai_dj.cli verify --plan evidence/hermes_plan1.json --master old_buggy.wav
pass: True
silence block: {"max_silent_run_in_transitions_ms": 0.0, "worst_region_s": null,
                "silent_hops_total": 589, "silence_ok": true}
true_peak: {"dbtp": -1.2, "limit_dbtp": -1.0, "ok": true}

# independent measurement of the same file:
longest silent run: 29.45 s @ 90.0 s
```

The verifier **sees** 589 silent hops and still reports `pass: true`. This is a
false PASS at the acceptance level: a DJ set with a half-minute hole would be
shipped as verified.

## 2. Decisions

### D12 — full-master continuity gate

`silence_ok` must be computed over the **entire** master, not only transition
windows. A silent run fails the gate unless it is deliberate:

- leading silence inside the renderer's own fade-in region;
- trailing silence inside the renderer's own fade-out region;
- a gap the plan explicitly declares as intentional (none exist today).

The transition-window measurement stays as **diagnostic detail**; it must no
longer be the verdict.

### D13 — unmeasurable ≠ pass (INCONCLUSIVE)

When a required measurement cannot be taken, the verdict is **INCONCLUSIVE**,
never PASS and never a fabricated number. `verify` already reports
`true_peak.ok: null` when ffmpeg is absent (D11) — but `hard_checks` uses
`peak_ok is not False`, so the run still ends in `pass: true`. Fix the verdict:

- `pass: true`  — every required check measured and within contract;
- `pass: false` — a required check was measured and failed;
- `pass: null` + `verdict: "INCONCLUSIVE"` — a required check could not be
  measured (missing ffmpeg, unreadable master, …).

Exit codes follow: 0 = PASS, 1 = FAIL, 2 = INCONCLUSIVE/usage-error.

## 6. Acceptance criteria

### 6.1 Silence gate — two tiers, whole master (D12)

Detect **two independent classes** on 50 ms RMS blocks, over the **entire** master:

| Class | Level | Min run | Result |
|---|---|---|---|
| Digital / near-digital silence | ≤ −90 dBFS | ≥ 0.5 s | **FAIL** |
| Low-level near-silence | ≤ −60 dBFS | ≥ 2.0 s | **FAIL** |
| Short-term loudness (3 s window) | — | — | diagnostic only |

The 29.45 s hole must be caught by **both** tiers. The transition-window figure
stays as diagnostic detail only.

Three rules are fixed:

- **A — multi-channel RMS, never mono.** `mono = data.mean(axis=1)` is WRONG:
  anti-phase L/R cancels to near-zero while both channels carry audio. Compute
  `RMS = sqrt( sum_c sum_n x[n,c]^2 / (N*C) )` then convert to dBFS. Also report
  per-channel RMS and flag a dead channel separately.
- **B — fade exemption from the renderer's real sample range.** Do NOT exempt an
  arbitrary first/last N seconds. Exempt only samples inside the fade-in/out the
  renderer actually declared, with a fixed bound. Every region inside an exempt
  range still appears in the report (auditability).
- **C — run length in samples, not float accumulation.** All thresholds are
  compared on sample index at the master's sample rate; state `>=` explicitly;
  add boundary fixtures at exactly 0.5 s and 2.0 s.

### 6.2 Verdict contract (D13)

`verdict` is the single source of truth; `pass` is a compatibility field. No
`blocking` field (two sources of truth can contradict).

| Condition | `pass` | exit code |
|---|---|---|
| every required check measured and within contract | `true` | 0 |
| at least one required check measured and failed | `false` | 1 |
| no FAIL, but a required measurement is missing | `null` | 2 |

- **A missing measurement is INCONCLUSIVE; a corrupt/unreadable master is FAIL.**
  If the WAV is required and is broken, absent, or undecodable → `pass: false`,
  not INCONCLUSIVE. Only *unmeasurable* things (no ffmpeg, no reference) are
  INCONCLUSIVE.
- **FAIL must not be masked by INCONCLUSIVE**: if ffmpeg is missing AND the
  continuity gate already failed, the verdict is FAIL.
- Reserve exit code 2 for INCONCLUSIVE; use a distinct code (e.g. 64) for CLI
  usage errors. A usage error must not emit a report with a valid-looking verdict.
- `checks` entries carry `status` ∈ {`PASS`, `FAIL`, `INCONCLUSIVE`} with a
  `reason` when not PASS. Never use `pass is not False` style aggregation.

### 6.3 Evidence required
